# Research Formulation & PICO Framework

This document outlines the core Research Question (RQ) of our study, framed using the PICO (Population, Intervention, Comparison, Outcome) methodology, and provides a direct mapping to the empirical evidence extracted from our Systematic Literature Review (SLR) of 9 primary studies.

## Core Research Question
> **Could GPT-4 automatic generation of unit test cases (I) compared to student-written manual test cases (C) achieve >=80% branch coverage and >=60% mutation score (O) when applied to Java/Python functions at medium cyclomatic complexity (P)?**

---

## The PICO Matrix Specification

### 1. Population (P): Java & Python Methods at Medium CC
* **Granularity & Target**: Function-level and method-level units in standard **Java** and **Python** codebases.
* **Complexity Level**: Medium Cyclomatic Complexity (CC ranges from 5 to 15). This represents methods with realistic logic (conditionals, nested branches, loops) rather than simple linear scripts or overly complex spaghetti code.
* **SLR Evidence Mapping**:
  * **Java Language Context**: Evaluated in 5 primary studies (`AX002`, `AX005`, `AX006`, `AX007`, `CORE001`).
  * **Python Language Context**: Evaluated in 6 primary studies (`AX001`, `AX002`, `AX003`, `AX007`, `CORE001`, `AX009`).
  * **Complexity Impact**: `AX005` confirms that cyclomatic complexity represents a major bottleneck for LLM test generation. `AX007` implements method slicing (HITS) as a divide-and-conquer strategy to handle CC boundaries.

### 2. Intervention (I): GPT-4 Automated Test Suite Generation
* **Core Technology**: The **GPT-4 series** models (GPT-4, GPT-4o, GPT-4-Turbo) executing autonomous test generation.
* **Prompt Engineering Strategies**:
  * **Coverage Optimization**: `AX001` utilizes covered code elimination in multiple feedback turns to force the LLM to target untested branches.
  * **Self-Healing Loop**: `AX002` investigates iterative error-repair prompt cycles to fix compiling errors.
  * **Context Amplification**: `AX006` inserts static call-chain dependency context into the LLM prompt. `CORE001` (KTester) injects global project and testing knowledge.

### 3. Comparison (C): Student-Written vs. Professional vs. Automated Baselines
* **Human Manual Baseline**:
  * **Real-world Developers**: `AX003` compares GPT-4 against professional developers using TestEval. `AX009` uses original open-source developer-written test suites.
  * **Our Unique Context**: Manual unit tests written by software engineering students representing the human baseline in academic and capstone settings. *No existing paper evaluates this specific student baseline, defining our project's core empirical gap.*
* **Automated Baselines**:
  * Traditional Search-Based Software Testing (SBST) like EvoSuite evaluated in `AX005` and `AX007`.
  * Advanced plain LLM generation tools like PANTA evaluated in `AX006` and `CORE001`.

### 4. Target Outcomes (O): Dual-Metric Quality Threshold
* **Branch Coverage >= 80%**: Assessed via structural coverage tools (JaCoCo for Java, coverage.py for Python).
  * Evaluated across 7 of our SLR papers (`AX001`, `AX003`, `AX005`, `AX006`, `AX007`, `CORE001`, `AX009`). Studies show that coverage degrades on high-complexity methods (`AX003`, `AX005`).
* **Mutation Score >= 60%**: Assessed via mutation testing engines (PITest for Java, MutPy/mutmut for Python) to measure semantic fault detection.
  * Evaluated by `AX003` and `AX007`. `AX003` warns that GPT-4's mutation scores on un-leaked complex code drops to ~41% even when coverage is high.
* **Dual-Metric Co-achievement**: Requires satisfying **both** thresholds simultaneously, addressing the gap where generated tests achieve high branch coverage but fail to detect actual bugs.
