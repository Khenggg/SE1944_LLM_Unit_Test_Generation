# Research Question — LLM for Unit Test Case Generation

**For Java/Python functions at medium cyclomatic complexity (P), could GPT-4o automatic generation of unit test cases (I) compared to manually written test cases (C) achieve >=30.22% branch coverage and >=40.21% mutation score (O)?**

---

## PICO Board

| Element | Description |
|---|---|
| **P – Population** | Java/Python functions at medium cyclomatic complexity (typically CC = 5–15) |
| **I – Intervention** | GPT-4o automatic generation of unit test cases |
| **C – Comparison** | Manually written test cases (developer-written / student-written) |
| **O – Outcome** | ≥30.22% branch coverage **and** ≥40.21% mutation score (with a ≥4.0% floor) |

### Detailed Breakdown

#### Population (P)

- **Language**: Java and/or Python source code.
- **Granularity**: Function-level or method-level units (not class-level or project-level testing as a whole, unless data can be isolated at the method level).
- **Complexity**: Medium cyclomatic complexity (CC ≈ 5–15). This represents code with a moderate number of execution paths, decision points, loops, or conditional statements. Measured via tools such as Lizard (Python/Java), Radon (Python), or PMD/Metrics (Java).

#### Intervention (I)

- **Tool**: GPT-4o (specifically, the version released on August 6, 2024, denoted as `gpt-4o-2024-08-06`). According to empirical literature (SS014, SS080), the GPT-4o model provides optimal cost-effectiveness, fast generation speeds, and strong zero-shot reasoning capabilities in code generation compared to earlier GPT-4 iterations.
- **Task**: Automatic generation of unit test cases directly from the source code under test.
- **Method**: Prompting techniques including zero-shot, few-shot, chain-of-thought, or structured template prompting.
- **Output**: Syntactically valid, compilable, and executable unit test suites (e.g., JUnit for Java, pytest/unittest for Python).

#### Comparison (C)

- **Baseline**: Manually written test cases authored by human developers (professionals, open-source contributors) or students.
- **Context**: Hand-crafted test suites representing standard developer effort (e.g., tests from project repositories, coding assignments, or benchmark baselines).
- **Secondary Comparison** (Optional): Performance against established automated test generation tools (e.g., EvoSuite, Randoop, CodaMosa) may be reported, but a human baseline is required.

#### Outcome (O)

- **Branch Coverage ≥ 30.22%**: The percentage of decision branches (e.g., if/else conditions, loops) executed by the generated test suite, measured using tools such as JaCoCo or Cobertura (Java) and coverage.py (Python).
- **Mutation Score ≥ 40.21% (Floor ≥ 4.0%)**: The percentage of seeded semantic faults (mutants) successfully killed by the test suite, measured using mutation testing engines such as PIT / PITest (Java) and MutPy / mutmut (Python).
- **Success Criterion**: The study must evaluate whether GPT-4o-generated tests can achieve both thresholds simultaneously (or exceed the human baseline of ≥4.0% mutation score) to answer the RQ in the affirmative.

> [!NOTE]
> **Threshold Adjustment Notice:**
> The original baseline targets were initially set to ideal developer standards (≥80% branch coverage and ≥60% mutation score). However, as our systematic literature review progressed, we aligned our expectations with realistic state-of-the-art averages. Empirical data from the UnLeakedTestBench (ULT) in SS040 demonstrates that LLMs achieve an average of 30.22% branch coverage and 40.21% mutation score on real-world functions of medium complexity. Thus, the main outcome targets are adjusted to ≥30.22% branch coverage and ≥40.21% mutation score. Additionally, we set a baseline mutation score floor of ≥4.0% (based on standard benchmarks from literature like GS005) to ensure generated tests have non-trivial fault detection capacity when compared to student-written tests.
