# Research Question Final

> [!NOTE]
> Please note that this document represents the "technical final RQ" up until this point in the research synthesis process. This should not be considered the exact, absolute final RQ, as there is one more major phase incoming (RBL-3) that would necessitate further refinements to these questions.

## Topic

LLM for Unit Test Case Generation.

## Main Research Question

For Java functions from the HumanEval-Java benchmark, can GPT-4o-mini-generated unit tests (using model version gpt-4o-mini-2024-07-18 under zero-shot prompting) achieve a branch coverage of >=30.22%, a mutation score floor of >=4.0%, and a mutation score target of >=40.21%, and how do their performance metrics compare with EvoSuite-generated unit tests under fixed 1-, 3-, and 5-minute budgets on the exact same functions?

> RBL-4 scope amendment: student-written benchmark tests remain the original motivation and future comparison target. This run has no validated per-function student measurements in the same pipeline; therefore, EvoSuite is the operational comparator only. EvoSuite results must not be reported as student results. See [the amendment](amendments/rbl4-operational-baseline.md).

## Sub-questions

| RQ | Question | Main Metric |
| --- | --- | --- |
| RQ1 | Do GPT-4o-mini-generated unit tests achieve a branch coverage of >=30.22% on the selected Java functions from the HumanEval-Java benchmark? | Branch coverage |
| RQ2 | Do GPT-4o-mini-generated unit tests achieve a mutation score of >=4.0% (empirical floor) and >=40.21% (target) on the exact same selected functions? | Mutation score |
| RQ3 | At each fixed EvoSuite budget (1, 3, and 5 minutes), is there a statistically significant difference in branch coverage and mutation score between GPT-4o-mini-generated and EvoSuite-generated unit tests evaluated on the same functions? | Paired metric difference per budget |
| RQ4 | Do GPT-4o-mini-generated unit tests achieve both the branch coverage threshold (>=30.22%) and the mutation score floor threshold (>=4.0%) simultaneously for a statistically significant majority (over 50%) of the functions? | Simultaneous success rate |
| RQ5 | What are the predominant failure patterns and technical limitations (e.g., compilation or execution issues) that prevent GPT-4o-mini-generated unit tests from reaching these thresholds? | Compilation/pass status; qualitative failure analysis |

## PICO Framework

| Component | Description |
| --- | --- |
| **P - Population** | Java functions from the HumanEval-Java benchmark, utilizing a dataset scale of 63 representative functions. |
| **I - Intervention** | Automated unit test suites generated by GPT-4o-mini (specifically version `gpt-4o-mini-2024-07-18`) utilizing a standardized, fixed zero-shot prompt protocol with `temperature = 0` to ensure reproducibility. |
| **C - Comparison** | EvoSuite-generated unit test suites under separate fixed budgets of 1, 3, and 5 minutes on the same 63 SUT. The student-written benchmark remains deferred because comparable measurements are unavailable. |
| **O - Outcome** | Achievement of branch coverage >=30.22% (GS017 floor), mutation score floor >=4.0% (GS005 floor), and mutation score target >=40.21% (GS017 target); simultaneous success rate >50% (Exact Binomial Test); and paired statistical comparison. |

## Metrics & Thresholds

| Metric | Threshold / Usage | Recommended Tooling |
| --- | --- | --- |
| Branch coverage | Primary threshold: >=30.22% (empirical floor from GS017) | JaCoCo for Java |
| Mutation score (Floor) | Floor threshold: >=4.0% (empirical floor from GS005) | PIT/PiTest for Java |
| Mutation score (Target) | Target threshold: >=40.21% (empirical target from GS017) | PIT/PiTest for Java |
| Simultaneous success rate | Dual success (BC >= 30.22% and MS >= 4.0%) achieved for >50% of the functions | Exact Binomial Test |
| Compile/pass status | Generated tests must successfully compile and execute before coverage and mutation metrics can be considered valid | Maven/Gradle for Java |
| Paired difference | Direct comparison between GPT-generated and EvoSuite-generated tests on the exact same functions, analysed separately for each time budget | Paired Wilcoxon signed-rank test with Holm correction across budget/metric tests |

## Scope & Threshold Rationale

The consolidated evidence from the Systematic Literature Review demonstrates that the highest quality, most reliable results are predominantly achieved by state-of-the-art models. To manage API cost during execution while maintaining high capability, the final research questions explicitly target GPT-4o-mini-generated unit tests (specifically version `gpt-4o-mini-2024-07-18` with temperature = 0 to guarantee deterministic, reproducible outputs).

**Threshold Justification:**
1. **Branch Coverage (>=30.22%):** Derived from Paper [GS017] / [010] (Huang et al., 2026), representing the average branch coverage achieved by major LLMs on real-world functions under the data-leakage-free ULT (UnLeakedTestBench) benchmark.
2. **Mutation Score Floor (>=4.0%):** Derived from Paper [GS005] / [026] (Wang et al., 2026 - MUTGEN), which represents the empirical floor in the evidence table and serves as a critical warning against evaluating test suites solely on code coverage (where 100% coverage was observed to pair with only a 4% mutation score).
3. **Mutation Score Target (>=40.21%):** Derived from Paper [GS017] / [010] (Huang et al., 2026), representing the average mutation score achieved by SOTA models on the ULT benchmark.

These values provide empirically grounded, scientifically sound thresholds for evaluating LLM test generation efficacy in a realistic scenario.
